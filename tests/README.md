# Quantivis Test Suite

End-to-end and load-testing framework. **No scenario runs automatically.** All execution is manual and gated.

## Layout

```
tests/
├── e2e/                  # Playwright browser tests (smoke, small, long-session)
├── load/                 # k6 API/load/ingestion tests + supporting Node scripts
│   ├── lib/              # shared k6 helpers (auth, guard, observability, ...)
│   ├── scenarios/        # k6 entrypoints per stage
│   ├── workflows/        # composable per-stage steps
│   ├── inventory/        # edge-function coverage matrix
│   ├── integrity/        # post-run DB + queued-ingest integrity checks
│   ├── release-gate/     # GO/NO-GO aggregator
│   ├── seed-users.mjs
│   ├── teardown.mjs
│   └── verify-teardown.mjs
├── PREREQUISITES.md      # MUST be satisfied before any certifying run
└── README.md             # this file
```

## Prerequisites (HARD GATE)

Read [`PREREQUISITES.md`](./PREREQUISITES.md).

F-1 (OAuth callback double-exchange) and F-2 (stale dynamic chunk recovery) have source-level fixes in the current tree, but a certifying test must still prove that the target environment is running the intended release. After verifying the deployed target SHA, set:

```bash
LOAD_PREREQ_CONFIRMED=yes
```

`LOAD_PREREQ_WAIVED=yes` is only for explicitly non-certifying diagnostics and must not be used as release or enterprise-scale evidence.

## Tools

- **k6** for API and ingestion load (`brew install k6` or see k6 installation docs)
- **Playwright** for browser tests (`npx playwright install chromium`)
- **Node 20+** for seed/teardown/integrity/inventory scripts

## Environment

Copy `.env.loadtest.example` to `.env.loadtest` and fill in the values relevant to the stage:

```bash
LOAD_TARGET=staging
LOAD_BASE_URL=https://staging.quantivis.io
LOAD_SUPABASE_URL=
LOAD_SUPABASE_ANON_KEY=
LOAD_ORG_A_ID=
LOAD_ORG_B_ID=
LOAD_USERS_FILE=tests/load/.users.json
LOAD_AI=mock
LOAD_AI_BUDGET_USD=5
LOAD_PREREQ_CONFIRMED=yes
LOAD_PREREQ_WAIVED=
SUPABASE_SERVICE_ROLE_KEY=   # staging only
```

For enterprise queued-ingestion certification also set:

```bash
LOAD_INGEST_API_KEY=
LOAD_INGEST_DATASET_ID=
LOAD_RUN_ID=enterprise-ingest-<unique-run-id>

# Optional tuning
LOAD_INGEST_RPS=20
LOAD_INGEST_BATCH=500
LOAD_INGEST_DURATION=1m
LOAD_INGEST_DRAIN_TIMEOUT_MS=600000
```

The default offered ingestion load is **20 requests/sec × 500 records = 10,000 records/sec**. This is a target generated by the test, not a performance claim. Certification requires both successful durable acceptance and the post-run persistence/integrity verifier.

Production is locked: requires both `LOAD_TARGET=production` and `LOAD_CONFIRM_PROD=I_UNDERSTAND`. The enterprise queued-ingestion certification scenario is intentionally staging-only.

## Running stages (manual only)

```bash
# 0. Verify gate + inventory
npm run load:matrix          # generates reports/edge-function-matrix.csv

# 1. Seed (staging service role required)
npm run load:seed

# 2. Smoke
npm run test:e2e:smoke
npm run load:smoke

# 3. Small browser/API load
npm run test:e2e:small
npm run load:small

# 4. Application concurrency load
npm run load:50
npm run load:100

# 5. Stress (1000 VU, API only, staging only, capped)
npm run load:1000

# 6. AI dependency chaos
npm run load:ai-chaos

# 7. Long browser session
npm run test:e2e:long

# 8. Enterprise ingestion: Volume + Velocity + durability
# Use the SAME LOAD_RUN_ID for the k6 run and the verifier.
npm run load:enterprise-ingest
npm run load:enterprise-ingest:verify

# 9. General integrity + teardown + release gate
npm run load:integrity
npm run load:teardown
npm run load:verify-teardown
npm run load:gate            # emits GO / NO GO
```

## What the enterprise ingestion test proves

The queued-ingestion path is separate from the ordinary 1/10/50/100/1000-VU application-load tests. The latter exercise concurrent users and APIs; they do **not** by themselves prove high-volume data ingestion.

`load:enterprise-ingest` exercises the durable queued ingestion endpoint and measures acceptance latency under records-per-second load. `load:enterprise-ingest:verify` then requires:

- every accepted sync job to reach a terminal state;
- zero stuck jobs;
- zero failed or partial jobs for a certifying run;
- zero failed/DLQ chunks;
- exact chunk accounting;
- persisted load-test metric count to match durable job progress.

A fast `202 Accepted` without successful drain is **not** a pass.

## Safety

- Two-org tenant isolation enforced for the ordinary application load suite (`org_loadtest_a` / `org_loadtest_b`).
- Enterprise ingestion uses an isolated staging data source + dataset whose API key and dataset organization must match.
- Email senders, unrelated connector pulls, demo seeders, and exports are name-blocked in the general load suite.
- AI calls are mocked unless `LOAD_AI=live` with an explicit budget.
- Writes are scoped to load-test organizations/datasets; teardown must be verified.
- 1000-VU run is hard-capped; no unbounded ramping.
- The durable metric queue has bounded admission/backpressure, visibility timeouts, retries, and a DLQ.

## Reports

General load scripts write to `tests/load/reports/` (gitignored). Reports carry request/trace context where supported.

For enterprise ingestion, preserve both the k6 summary and the JSON/console output from `load:enterprise-ingest:verify` with the tested release SHA. Those artifacts are the minimum evidence for any Volume/Velocity claim.

## Release gate

`npm run load:gate` parses the general load reports and emits **GO** or **NO GO** with per-criterion justification. Enterprise-scale certification additionally requires a passing `load:enterprise-ingest:verify` result for the same deployed release; the general release gate alone does not establish enterprise data-scale readiness.
